# Project Documentation

This document provides an overview of the project structure, how to add new modules, and how to connect them.

## Overall Project Structure

The repository is organized into several top-level directories:

*   **`APPs/`**: Contains various applications. These applications are typically composed of interconnected modules from the `modules/` directory. Each application has its own configuration, data files, hardware platform specifics, logging directories, and run scripts (e.g., `runcf_start*.sh`).
*   **`modules/`**: This is the core of the system, housing individual signal processing blocks or components. Each module follows a standardized structure, which is detailed in the "Module Structure" section.
*   **`hw_api/`**: Hardware Abstraction Layer. This directory contains code for interacting with specific hardware components, such as sound cards or USRP (Universal Software Radio Peripheral) devices. It provides a consistent interface for modules to access hardware.
*   **`sw_api/`**: Software API. This likely provides a standardized way for modules to communicate with each other or access common software services and utilities within the framework.
*   **`sw_daemons/`**: Contains software daemons, which are background processes that might manage overall system operations, inter-module communication, or scheduling.
*   **`scripts/`**: Includes various utility shell scripts. Notably, it contains scripts for creating new modules from templates (e.g., `create_module_templateSK15.sh`).
*   **`aloeSKs/`**: Appears to be related to "ALOE Stubs/Skeletons," possibly part of the ALOE framework, providing base implementations or templates.
*   **`aloeui/`**: Contains components for a user interface, likely named "aloeui," for interacting with the applications or modules.
*   **`JACK/`**: Holds integration code for the JACK Audio Connection Kit, a professional sound server API, allowing for low-latency audio and MIDI data routing between applications.
*   **`doc/`**: Contains general project documentation files.
*   **`utils/`**: Contains utility functions and tools used across different parts of the project.
*   **`matlab/`**: Contains MATLAB scripts and related files, likely used for simulation, testing, or verification of algorithms.

Other notable files/directories in the root:
*   **`configure.ac`, `Makefile.am`, `configure`**: These are part of the GNU Autotools build system.
*   **`README`**: Basic information about the project.
*   **`INSTALL`**: Generic instructions for building and installing projects using Autotools.

## Build System

The project uses the **GNU Autotools** suite for its build system. This is a common system for C/C++ projects on Unix-like systems. The main components are:

*   **`configure.ac`**: The main configuration file for `autoconf`. It contains tests for system features, dependencies, and sets up variables for the build process.
*   **`Makefile.am`**: Used by `automake` to generate `Makefile.in` files, which are then used by `configure` to create the final `Makefile`s. These files define what needs to be built and how.
*   **`configure`**: A script generated by `autoconf` (from `configure.ac`). When run (e.g., `./configure`), it checks the system environment and generates the `Makefile`s.
*   **`make`**: The standard command-line tool to start the compilation process using the generated `Makefile`s.

The typical build process is:
1.  Run `./configure` (potentially with options like `LIBS='-lpthread -lboost_system'`).
2.  Run `make` to compile the source code.
3.  Optionally, run `make install` to install the built programs and libraries.

Refer to the `INSTALL` file in the root directory for more generic details on using Autotools.

## Module Structure

Modules are the building blocks of applications within this framework and are located in the `modules/` directory. They generally follow a standardized directory structure, facilitating consistency and ease of navigation.

A typical module (e.g., `modules/MY_NEW_MODULE/`) would have the following subdirectories:

*   **`src/`**: This is where the primary C source code (.c files) and header files (.h files) for the module reside.
    *   Often contains `MY_NEW_MODULE.c` (main module logic), `MY_NEW_MODULE_functions.c` (helper functions), `MY_NEW_MODULE_params.h` (parameter definitions), and `MY_NEW_MODULE_interfaces.h` (definitions for how this module interacts with the outside world or other modules).
*   **`lnx_make/`**: Contains Linux-specific makefiles, typically a `Makefile.am` that integrates the module into the Autotools build system. This tells `automake` how to compile the source files in the `src/` directory.
*   **`interfaces/`**: Holds header files (.h) that define the public interface of the module. These files would be included by other modules or applications that need to interact with this module. It might also contain definitions of data structures or types passed to/from the module.
*   **`doc/`**: Intended for module-specific documentation. At a minimum, it might contain a `README` or `MY_NEW_MODULE.md` file explaining the module's purpose, parameters, and usage.
*   **`matlab/`**: Contains MATLAB scripts (.m files) and any associated files. These are often used for:
    *   Simulating the module's behavior.
    *   Verifying the C implementation against a MATLAB model.
    *   Generating test data or analyzing output.
    *   Sometimes includes a C file for a MEX interface, allowing the C code to be called directly from MATLAB (e.g., `MY_NEW_MODULE.c` within this directory, compiled to `MY_NEW_MODULE.mexglx`).
*   **`standalone/`**: Provides a way to test the module in isolation. It often contains:
    *   A `test_generate.c` or similar file that acts as a test harness or main program for the module.
    *   Specific Makefiles or build configurations for compiling the standalone test.
*   **`params/`**: (Present in many modules) Contains parameter configuration files (e.g., `MY_NEW_MODULE.params`). These files define default settings or specific configurations that the module can load at runtime.
*   **`aloe/`**: This directory appears in many modules and seems to be part of the "ALOE" framework. It might contain:
    *   Code related to the ALOE skeleton or infrastructure (`skeleton/`).
    *   External library linkage or data file definitions (`extern/`).
    *   Plotting or visualization utilities, possibly using Gnuplot (`gnuplot/`).
    *   Standalone test configurations specific to the ALOE framework.
*   **`debug_make/`**: (Present in some modules) Likely contains Makefiles specifically configured for easier debugging of the module.
*   **Eclipse Project Files (`.cproject`, `.project`, `.settings/`)**: These are often found within module directories, indicating that modules can be developed as separate projects within the Eclipse IDE.

This structure ensures that code, documentation, tests, and build instructions are organized logically for each module.

## Adding a New Module

This section describes the step-by-step process for creating a new module and integrating it into the project.

### Step 1: Create Module from Template using Script

The `scripts/` directory contains several shell scripts to automate the creation of new modules from templates. The most relevant script appears to be `create_module_templateSK15.sh` (or a similarly named one like `create_moduleALOE_SK18.sh` or `create_module_template4.sh` depending on the specific ALOE version/template you need - check the `scripts/` directory for the latest).

1.  **Navigate to the `scripts` directory:**
    ```bash
    cd scripts
    ```
2.  **Run the creation script:**
    Provide the desired name for your new module as an argument. Module names are typically in all uppercase (e.g., `MY_NEW_MODULE`).
    ```bash
    ./create_module_templateSK15.sh MY_NEW_MODULE
    ```
    (Replace `create_module_templateSK15.sh` with the most appropriate script if needed, and `MY_NEW_MODULE` with your chosen module name).

3.  **What the script does:**
    *   It copies a template module directory (e.g., `module_template3.ALOE1.6SK15`, which is itself a copy of `modules/module_template3`) into the `../modules/` directory under your new module's name (e.g., `../modules/MY_NEW_MODULE`).
    *   It then automatically performs a find-and-replace operation (`sed`) within the copied files to replace template names (e.g., `module_template3`) with your new module's name (`MY_NEW_MODULE`). This renaming occurs in:
        *   Makefiles (e.g., `test/Makefile`, `lnx_make/Makefile.am`)
        *   C source and header files in `src/`
        *   MATLAB script template names
        *   Eclipse project files (`.cproject`, `.project`)
    *   It also renames key files within the new module directory to match your module's name (e.g., `src/module_template3.c` becomes `src/MY_NEW_MODULE.c`).

After the script finishes, a new directory for your module will be created in `modules/MY_NEW_MODULE/` with the basic file structure and boilerplate code.

### Step 2: Implement Module Logic

Once the module structure is created, you need to implement its core logic and interfaces.

1.  **Implement C Code (`src/` directory):**
    *   **`MY_NEW_MODULE.c`**: This file will contain the main entry point and core processing logic for your module. The template will provide a basic structure.
    *   **`MY_NEW_MODULE_functions.c`**: Implement any helper or auxiliary functions here. This helps keep the main `.c` file cleaner.
    *   **`MY_NEW_MODULE_functions.h`**: Header file for the functions defined in `MY_NEW_MODULE_functions.c`.
    *   **`MY_NEW_MODULE.h`**: Main header file for your module. It might include function prototypes from `MY_NEW_MODULE.c` if they are intended to be called from within the module's own source files (e.g. by test code) but not necessarily part of the external interface.
    *   **`MY_NEW_MODULE_params.h`**: Define data structures and constants related to your module's parameters. The actual parameter values are typically loaded from `.params` files (see `params/` directory).
    *   **`MY_NEW_MODULE_interfaces.h`**: This is a crucial file. Define the data structures, function prototypes, and any other declarations that form the public API of your module. Other modules or applications will include this header (or a related one from the `interfaces/` directory) to use your module.

2.  **Define Public Interfaces (`interfaces/` directory):**
    *   The `interfaces/` directory in your module should contain the header files that other modules will `#include` to use your module.
    *   Often, `MY_NEW_MODULE_interfaces.h` from the `src/` directory is copied or symlinked here, or a more specific public interface file is created (e.g. `stats.h` seems to be a common one for statistics reporting).
    *   Ensure that only the necessary functions and data structures for external interaction are exposed here.

3.  **Update Module Documentation (`doc/` directory):**
    *   Open `doc/README` (or create `doc/MY_NEW_MODULE.md`) and write a clear description of what your module does, its inputs, outputs, and any important usage notes.
    *   If your module uses parameters, document them here or in a separate file.

4.  **Define Parameters (`params/` directory):**
    *   Edit or create `params/MY_NEW_MODULE.params`. This file should contain the default parameter values that your module will use. The module's C code (typically in `MY_NEW_MODULE_params.c` if it exists, or as part of `MY_NEW_MODULE.c`) will be responsible for parsing this file.

This step involves the primary development work for your module's functionality.

### Step 3: Integrate into the Build System

After creating the module and implementing its basic logic, you need to integrate it into the project's Autotools build system so it gets compiled.

1.  **Update `Makefile.am` in the `modules/` directory:**
    *   Open the `Makefile.am` file located in the main `modules/` directory (i.e., `modules/Makefile.am`).
    *   This file likely contains a list of subdirectories for each module, often in a variable like `SUBDIRS` or `DIST_SUBDIRS`.
    *   Add the name of your new module's directory (e.g., `MY_NEW_MODULE`) to this list. Ensure it's added in alphabetical order if that's the convention used.
    *   Example (illustrative):
        ```makefile
        # In modules/Makefile.am
        SUBDIRS =             ADSIMUL             CHANNEL_ANALYZER             ...
            MY_NEW_MODULE \ # Add your new module here
            ...
            UPLINK_SYNCHRO
        ```

2.  **Update Root `configure.ac` (If Necessary):**
    *   In many Autotools projects, adding a subdirectory to `modules/Makefile.am` is sufficient if it correctly points to your module's own `Makefile.am` (e.g., `modules/MY_NEW_MODULE/lnx_make/Makefile.am`).
    *   However, for some configurations or if new global build options are needed for your module, you might need to edit the main `configure.ac` file in the project's root directory. This step is less common for simply adding a new, typical module. If your module has special library dependencies that aren't already handled, you might need to add checks for them in `configure.ac`.

3.  **Run Autotools Commands:**
    *   After modifying any `.am` or `.ac` files, you need to regenerate the build system files.
    *   Navigate to the root directory of the project.
    *   If you modified `configure.ac` (or if it's the first time or you suspect issues), run `autoconf`:
        ```bash
        autoconf
        ```
    *   Then, run `automake --add-missing` to regenerate `Makefile.in` files:
        ```bash
        automake --add-missing
        ```
    *   Finally, run `configure`. The `create_module_templateSK15.sh` script had a commented-out line suggesting `LIBS='-lpthread -lboost_system'`. Use appropriate libraries required by your project/module. If unsure, check the existing `configure` command used for the project or consult other modules.
        ```bash
        ./configure LIBS='-lpthread -lboost_system' # Or other relevant LIBS
        ```

4.  **Compile the Project:**
    *   Now, run `make` to compile the entire project, including your new module.
        ```bash
        make
        ```
    *   If successful, your module's static library (e.g., `libMY_NEW_MODULE.a`) or executable should be built and placed in the appropriate subdirectory within `modules/MY_NEW_MODULE/lnx_make/bin/` or a similar location, depending on your `Makefile.am` settings. The compiled executables that are meant for system-wide use are often copied to `SWMAN_EXECS/linux/` by the build process.

### Step 4: Finalize Module-Specific Documentation

While initial documentation was mentioned in Step 2, ensure it's comprehensive now that the module is integrated.

*   **`doc/README` or `doc/MY_NEW_MODULE.md`**:
    *   Verify that it clearly explains the module's purpose, inputs, outputs, algorithms used, and any important usage instructions or limitations.
    *   Include an example of how to use the module if applicable.
*   **Parameters (`params/MY_NEW_MODULE.params`):**
    *   Ensure all parameters used by the module are listed in the `.params` file with sensible default values.
    *   Document the meaning of each parameter, its valid range, and its effect on the module's behavior, either in the `doc/README` or as comments within the `.params` file itself.

### Step 5: Implement and Run Tests

Thorough testing is crucial to ensure your module works correctly in isolation and when integrated with other modules.

1.  **Standalone Testing (`standalone/` directory):**
    *   The template likely created a `test_generate.c` (or similar) in the `standalone/` directory.
    *   Modify this file to create a test harness for your module. This typically involves:
        *   Including your module's interface header.
        *   Creating sample input data.
        *   Calling your module's main processing functions.
        *   Verifying the output against expected results.
        *   Printing status messages (pass/fail).
    *   Compile and run this standalone test. The `standalone/` directory might have its own `Makefile` or instructions for building the test executable.

2.  **MATLAB Testing/Verification (`matlab/` directory):**
    *   If you have a MATLAB model of your module's functionality, use the scripts in the `matlab/` directory to:
        *   Compare the output of your C implementation with the MATLAB model using the same input data.
        *   Visualize data if helpful.
    *   The `verify.m` script often serves this purpose.
    *   If a MEX interface C file (e.g., `matlab/MY_NEW_MODULE.c`) was generated, compile it into a MEX file (e.g., `MY_NEW_MODULE.mexglx`) so you can call your C code directly from MATLAB for easier testing and comparison.

3.  **Integration Testing (within an Application):**
    *   Once the module passes standalone tests, the next step is to test it within a larger application by connecting it with other modules. This is covered more in the "Connecting Modules" and "Documenting Applications" sections.

By following these steps, you can create a new module, implement its functionality, integrate it into the build system, document it, and test it thoroughly.

### Step 4: Document Connecting Modules (Inter-Module Communication)

In this framework, modules within an application (`APPs/`) are typically not connected by direct C function calls or by including each other's header files in the traditional sense for primary data flow. Instead, connections and data flow are defined declaratively in application-specific configuration files (usually with a `.app` extension) and managed by a runtime environment.

**1. The `.app` Configuration File:**

*   Applications in the `APPs/` directory (e.g., `APPs/WAVEForms/CHAIN/`) use `.app` files (e.g., `SUI_REPORT.app`) to define the processing chain.
*   These files describe a directed graph of module instances (objects).
*   Each `object` block in an `.app` file specifies:
    *   `obj_name`: A unique name for this instance of the module within the application (e.g., `DATASOURCESINK`, `CRC_MODULE`, `FFT_PROCESSOR`).
    *   `exe_name`: The executable name of the module (e.g., `DATASOURCESINK_REPORTP21`, `CRC`, `FFT_IFFT`). These executables are typically built from the code in the `modules/` directory and might be located in `SWMAN_EXECS/linux/`.
    *   `inputs`: Defines how data flows into this module's input ports.
        *   `name`: The local input port name of this module (e.g., `input_0`, `control_signal`).
        *   `remote_itf`: The name of the output port on the source module (e.g., `output_0`, `data_out`).
        *   `remote_obj`: The `obj_name` of the source module that provides the data for this input.
    *   `outputs`: Defines how data flows from this module's output ports to other modules.
        *   `name`: The local output port name of this module (e.g., `output_0`, `debug_stats`).
        *   `remote_itf`: The name of the input port on the destination module.
        *   `remote_obj`: The `obj_name` of the destination module that will receive the data from this output.
    *   `force_pe` (optional): This likely stands for "Force Processing Element" and might be used to hint or assign the module's execution to a specific CPU core or processing thread, relevant for performance tuning in multi-core systems.

**Example from `APPs/WAVEForms/CHAIN/SUI_REPORT.app`:**

```
object {
	obj_name=CRC          # Instance name for the CRC module
	exe_name=CRC          # Executable for the CRC module
	inputs {
		name=input_0      # Input port of this CRC instance
		remote_itf=output_0 # Connects to output_0 of DATASOURCESINK
		remote_obj=DATASOURCESINK
	}
	outputs {
		name=output_0     # Output port of this CRC instance
		remote_itf=input_0 # Connects to input_0 of LTETURBOTX
		remote_obj=LTETURBOTX
	}
}

object {
	obj_name=LTETURBOTX
	exe_name=LTEturboCOD2
	inputs {
		name=input_0
		remote_itf=output_0
		remote_obj=CRC      # Receives data from the CRC module instance
	}
	outputs {
		name=output_0
		remote_itf=input_0
		remote_obj=SCRAMBLING
	}
}
```
In this example, the `output_0` of the `DATASOURCESINK` module instance is connected to `input_0` of the `CRC` module instance. Then, the `output_0` of `CRC` is connected to `input_0` of the `LTETURBOTX` module instance.

**2. The Runtime Environment (`runcf`):**

*   Applications are typically launched using a shell script (e.g., `runcf_start_SIMUL.sh` or `runcf_start_RTJACK.sh`).
*   These scripts often invoke a command like `runcf -c hwplatform/platform.conf`.
*   `runcf` is a runtime configuration executable. It reads:
    *   The platform configuration (`hwplatform/platform.conf`), which specifies hardware details, memory allocation, and other system-level parameters.
    *   The `.app` file (the specific file might be implicitly defined or referenced within `platform.conf` or other configurations).
*   The `runcf` environment is responsible for:
    *   Loading the executables for each module defined in the `.app` file.
    *   Setting up the connections between modules as specified by the `inputs` and `outputs` blocks.
    *   Managing the data flow between modules at runtime. Modules use APIs provided by the framework (likely from `sw_api/` or `hw_api/`) to read data from their input ports and write data to their output ports.

**3. Module Implementation for Connectivity:**

*   When developing a module, you define its input and output interfaces (ports) in its C code (e.g., in `MY_NEW_MODULE_interfaces.h` and implemented in `MY_NEW_MODULE.c`).
*   The module's main processing loop will read data from its input ports, process it, and write results to its output ports using the framework's APIs.
*   The module itself does not need to know the specific upstream or downstream modules it's connected to; this is abstracted by the runtime environment and the `.app` file configuration.

**4. Parameters and Configuration:**

*   Each module instance in the `.app` file will typically have its parameters configured in the `paramscfg/` directory of the application. For example, the `CRC` module instance named `CRC` would load its settings from `paramscfg/CRC.params` (or a file specified by `runcf` or the platform configuration).

This declarative, graph-based approach allows for flexible construction and reconfiguration of complex processing chains without recompiling individual modules. To change the application's behavior or data flow, you would typically modify the `.app` file and potentially parameter files.

## Documenting Applications (`APPs/`)

Applications are specific configurations or instances of processing chains that utilize the modules from the `modules/` directory. They are found in the `APPs/` directory, with each subdirectory representing a distinct application (e.g., `APPs/WAVEForms/CHAIN/`, `APPs/JACKTools/CAPTURE_CHANNEL/`).

**1. Application Directory Structure:**

A typical application directory contains the following key components:

*   **`.app` files (e.g., `SUI_REPORT.app`, `CAPTURE_CHANNEL.app`):**
    *   These are the core of the application, defining the graph of modules and their interconnections, as detailed in the "Connecting Modules" section.
    *   An application directory might contain multiple `.app` files, representing different configurations or modes of operation for that application.
*   **`paramscfg/`**:
    *   This subdirectory stores the parameter configuration files (`.params`) for each module instance used in the `.app` files. For example, if `SUI_REPORT.app` uses a module instance named `CRC_INSTANCE` with `exe_name=CRC`, then `paramscfg/CRC_INSTANCE.params` (or `paramscfg/CRC.params` if names are reused or defaulted) would hold its specific settings.
*   **`hwplatform/`**:
    *   Contains hardware and platform-specific configurations.
    *   `platform.conf`: Defines the overall hardware setup, memory mapping, and potentially which `.app` file to load by default for the `runcf` utility.
    *   `scheduling.conf`: May define scheduling priorities or affinities for different modules or threads.
    *   `xitf.conf`: Could be related to interface configurations.
*   **`runcf_start_*.sh` scripts (e.g., `runcf_start_SIMUL.sh`, `runcf_start_RTJACK.sh`):**
    *   Shell scripts used to launch the application.
    *   They typically first call `./stop_runcf.sh` to terminate any existing instances.
    *   Then, they execute `runcf -c hwplatform/platform.conf` (or a similar command) to start the runtime environment, which loads and connects modules based on the `.app` and parameter files.
    *   Different `runcf_start_*.sh` scripts might point to different `platform.conf` files or set different environment variables for simulation mode, real-time JACK execution, etc.
*   **`data/`**: Holds any input data files required by the application or modules within it (e.g., text files, images, waveform definitions).
*   **`logs/`**: When the application runs, modules typically write their log files into this directory (e.g., `CRC.log`, `FFT.log`). This is essential for debugging and monitoring.
*   **`docs/`**: Application-specific documentation, if any.
*   **`make_installALL.sh`, `make_installNEW.sh`**: Scripts possibly used to prepare or install the application or its components, though the main build is handled by the top-level Autotools system.

**2. How Applications Work:**

1.  The user executes a `runcf_start_*.sh` script.
2.  The `runcf` program is launched.
3.  `runcf` reads the specified `platform.conf` file to understand the hardware environment and potentially the default `.app` file to load.
4.  `runcf` parses the relevant `.app` file to identify all module instances (`obj_name`, `exe_name`) and their connections (`inputs`, `outputs`).
5.  For each module instance, `runcf` loads its corresponding parameter file from `paramscfg/`.
6.  `runcf` then instantiates all modules and establishes the data pathways between them as defined in the `.app` file, effectively building the processing graph at runtime.

**3. Adding a New Module Instance to an Application:**

To incorporate an existing, compiled module (e.g., `MY_NEW_MODULE`) into an application:

1.  **Edit the `.app` file:**
    *   Decide where in the processing chain your new module instance fits.
    *   Add a new `object` block for your module instance:
        ```
        object {
            obj_name=MY_MODULE_INSTANCE_NAME  # e.g., MY_NEW_MODULE_01
            exe_name=MY_NEW_MODULE            # The executable name of your module
            inputs {
                name=input_0                  # Local input port of your module
                remote_itf=output_X           # Output port of the preceding module
                remote_obj=PRECEDING_MODULE_INSTANCE_NAME
            }
            outputs {
                name=output_0                 # Local output port of your module
                remote_itf=input_Y            # Input port of the succeeding module
                remote_obj=SUCCEEDING_MODULE_INSTANCE_NAME
            }
            # Add more inputs/outputs as needed
        }
        ```
    *   Modify the `inputs` or `outputs` sections of the preceding and succeeding module instances to connect to your new module instance's `obj_name` and its respective ports (`remote_itf`).
2.  **Add Parameter File:**
    *   If your module requires parameters, create a `MY_MODULE_INSTANCE_NAME.params` (or `MY_NEW_MODULE.params`) file in the application's `paramscfg/` directory with the desired settings.
3.  **Verify Connections:**
    *   Carefully check all `remote_obj` and `remote_itf` references in the `.app` file to ensure the graph is correctly wired. Mismatched names or incorrect port references are common sources of errors.
4.  **Test:**
    *   Run the application using its `runcf_start_*.sh` script and check the `logs/` directory for logs from your new module instance and observe the application's behavior.

**4. Creating a New Application:**

While there isn't a dedicated script observed for creating a *new* application, the process would involve:

1.  Creating a new directory in `APPs/` (e.g., `APPs/MY_NEW_APP/`).
2.  Copying the structure from an existing, similar application (e.g., `hwplatform/`, `paramscfg/`, a sample `.app` file, a `runcf_start_*.sh` script).
3.  Customizing the `.app` file to define the specific module chain for your new application.
4.  Populating `paramscfg/` with the necessary parameter files for all modules used.
5.  Modifying `hwplatform/platform.conf` and the `runcf_start_*.sh` script as needed.
6.  Adding any required data files to `data/`.

## Best Practices

Adhering to best practices will help maintain the quality, consistency, and maintainability of the codebase.

*   **Module Naming Conventions:**
    *   Module directory names and `exe_name` values are typically in `UPPERCASE_SNAKE_CASE` (e.g., `MY_MODULE`, `LTE_TURBO_COD`).
    *   C source files (`.c`) and header files (`.h`) within a module often follow the module's name (e.g., `MY_MODULE.c`, `MY_MODULE_functions.h`).
    *   Instance names (`obj_name`) in `.app` files also tend to be `UPPERCASE_SNAKE_CASE`.
*   **Clear Interfaces:**
    *   Define clean, well-documented interfaces for your modules in the `interfaces/` directory (or `src/*_interfaces.h`).
    *   Minimize exposed functions and data structures to only what is necessary for interaction with other modules.
*   **Comprehensive Documentation:**
    *   **Module Documentation (`modules/MY_MODULE/doc/`):** Each module should have a `README.md` or similar file explaining its purpose, algorithm, parameters, input/output data structures, and any usage notes.
    *   **Parameter Documentation (`modules/MY_MODULE/params/`):** Clearly document each parameter in the `.params` file (e.g., using comments) or in the module's `doc/README.md`. Explain its meaning, valid range, and impact.
    *   **Application Documentation (`APPs/MY_APP/docs/`):** For complex applications, provide a document explaining the overall chain, its purpose, and how to run it.
